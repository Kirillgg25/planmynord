# PlanMyNord Flights: анализ и план

Дата проверки: 18 сентября 2026. Этапы 1–2. Реализация после согласования.

## Существующий проект

- Node.js, CommonJS, Express 4; запуск `node server.js`, порт по умолчанию 3000. React и сборщика нет: HTML/CSS и браузерные ES modules.
- `server.js` содержит API, сессии, авторизацию, платежи, SQLite и опциональное подключение PostgreSQL. Flights не требует изменения этих данных или платежного процесса.
- Реальный frontend обслуживается из `public/`. Корневые копии HTML/CSS/JS не являются источником для HTTP. Это явно описано в `PUBLIC_FILES.md`.
- `lib/public-site.js` содержит список разрешённых публичных файлов; новые assets должны быть внесены туда. Чистые адреса регистрируются в `cleanPageRoutes` в конце `server.js`.
- Уже существует `/tickets`: `public/tickets.html`, `public/tickets.css`, `public/js/tickets-page.js`. Там ограниченный список аэропортов отправления, норвежские назначения, подготовка ссылок Google Flights/Kiwi/Skyscanner. Получения предложений и цен нет.
- Переиспользуем логотип, `.topbar`/`.topnav`, светлые карточки и синие акценты, `auth.js`, `html-utils.js`, `popup-controller.js`, `date-picker.js`. Календарь необходимо проверить на доступность на телефоне и клавиатурой.
- `public/js/i18n.js` уже поддерживает no/en/ru, `t()`, атрибуты `data-i18n` и событие `languagechange`. Добавим пространство ключей `flights.*`.
- Валютный переключатель можно использовать, но фиксированные курсы из `currency.js` нельзя применять к реальным авиапредложениям: показываем сумму и валюту поставщика; другая валюта — новый поиск, если поддерживается.
- Helmet/CSP, express-rate-limit, dotenv уже установлены. Новые зависимости на первом этапе реализации не обязательны; версию Node для встроенного fetch проверим перед реализацией.
- `UBUNTU_SERVER.md` описывает systemd; это инструкция, не подтверждение текущего состояния сервера. Сервер, Cloudflare и VPN в этой задаче не изменялись.
- `git status` здесь не работает: `.git` не содержит действующего репозитория. Перед коммитом потребуется рабочий checkout; это не препятствует локальному прототипу.

## Поставщики

### Travelpayouts / Aviasales

Лучшее функциональное соответствие модели «поиск → внешний продавец», но доступ условный: минимум 50 000 подтверждённых MAU, затем индивидуальное одобрение. Без этого порога обещать доступ нельзя. [Условия доступа](https://support.travelpayouts.com/hc/en-us/articles/210995808).

Для новой интеграции нужен новый Search API, а не старый endpoint. Новый API выполняет живой поиск, поддерживает направления по миру, типы пассажиров, класс, валюту/рынок; базовый лимит — 100 запросов в час на IP пользователя. Поиск асинхронный, результаты приходят постепенно; отдельное получение ссылки происходит по клику. Реальное покрытие и принимаемые аэропортовые/городские коды нужно проверить в одобренном аккаунте, особенно для рынка Норвегии. [Текущая спецификация](https://support.travelpayouts.com/hc/en-us/articles/30565016140434).

Поиск только по действию пользователя, никаких фоновых поисков и предварительного получения booking-ссылок. Нельзя объединять с API других авиаметапоисковиков; переключаемый адаптер не означает разрешение на одновременную агрегацию. Есть требования конверсии 9% search→click и 5% click→purchase, а результаты необходимо закрыть от индексации. [Правила](https://support.travelpayouts.com/hc/en-us/articles/34788165535250-Search-API-usage-rules).

Историческая документация называла API бесплатным; актуальную стоимость и квоты нового доступа нужно подтвердить в партнёрском соглашении. Это не обещание бесплатного production. [Старая версия](https://support.travelpayouts.com/hc/en-us/articles/203956173-Aviasales-Flights-Search-API-old-version).

Data API выдаёт кэшированные цены, а не заменяет живой поиск. Можно применять для отдельного вдохновляющего блока с датой обнаружения, но не выдавать его за доступные к покупке предложения. [Официальный Data API](https://github.com/travelpayouts/api-docs/blob/master/source/index.html.md).

Документация регистрации не гарантирует одобрение проекта из Норвегии или конкретный способ выплаты: страну проживания, доступные программы и выплаты проверяем при onboarding. [Регистрация](https://support.travelpayouts.com/hc/en-us/articles/11394852618642-How-to-use-Travelpayouts-Quick-Start-Guide).

### Amadeus

Self-Service больше нельзя планировать как простой новый доступ: официальный портал сообщает о закрытии 17 июля; организация разработчиков архивирована 17 июля 2026, руководство помечено deprecated. Доступ Enterprise обсуждается отдельно. [Портал](https://developers.amadeus.com/self-service/category/hotels), [официальный GitHub](https://github.com/amadeus4dev), [руководство](https://raw.githubusercontent.com/amadeus4dev/developer-guides/master/README.md).

Исторический Flight Offers Search давал актуальные предложения, Flight Offers Price — перепроверку. Но это booking API без универсальной affiliate-ссылки продавца; Self-Service имел существенные ограничения покрытия. Старые бесплатные квоты и цены нельзя считать актуальным коммерческим предложением. Для Норвегии нужны подтверждение Enterprise onboarding, стоимость, покрытие и отдельный продукт/договор с поддержкой внешнего бронирования. [Архивная официальная FAQ](https://admin.developers.amadeus.com/self-service/apis-docs/guides/developer-guides/faq/).

Практический вариант — договор с Enterprise/партнёром, предоставляющим настоящий metasearch deep link. Самостоятельно построенная ссылка не сохраняет предложение Amadeus. Встроенное бронирование с consolidator меняет бизнес-модель и не входит в текущую задачу.

### Duffel

Живые предложения сотен авиакомпаний по миру; не все рейсы гарантированно покрыты. Есть истечение offer и обновление/проверка цены. API ориентирован на создание и сопровождение заказов, а не сравнение независимых продавцов с affiliate-переходом. [Flights](https://duffel.com/flights), [Offers](https://duffel.com/docs/api/offers).

Duffel Links открывает hosted search-and-book, однако заказы доступны вашей организации, остаются обязанности по подтверждениям и сопровождению. Это технически рабочий hosted checkout для подходящего продавца, но не эквивалент требуемому affiliate-поисковику. Требуется страна организации, поддерживаемая Duffel Payments; Норвегии в опубликованном списке нет. Подтвердить возможность норвежского onboarding следует у Duffel, не подменяя страну регистрации. [Links](https://duffel.com/docs/guides/duffel-links), [страны Payments](https://help.duffel.com/hc/en-gb/articles/4409049043730-In-which-countries-is-Duffel-Payments-available).

Публичный USD-тариф: $3 за подтверждённый заказ, 1% managed content, $2 за платную дополнительную услугу; $0.005 за поиск сверх отношения 1500:1. Для search-only без заказов это плохое экономическое соответствие. Платежные/FX сборы и договорные условия рассматриваются отдельно. [Тарифы](https://duffel.com/pricing).

## Рекомендация

Архитектура с заменяемым поставщиком и сначала честный demo. Travelpayouts — первый кандидат только при подтверждении 50 000 MAU и одобрении. Если порога нет, ни один из трёх не подтверждён как доступное готовое решение для всего заданного сценария. Не подключать Duffel или старый Amadeus просто ради работающего API.

До API-доступа возможен официальный affiliate search form/White Label с внешними результатами, если инструмент доступен аккаунту. Это отдельный упрощённый вариант, без обещания собственного списка живых предложений. Собственный demo можно использовать для проверки интерфейса и будущего согласования.

## Предлагаемая архитектура

Публичные файлы: `public/flights.html`, `public/flights.css`, `public/js/flights-page.js`, при необходимости `public/js/flights-filters.js`. Серверные: `lib/flights/router.js`, `service.js`, `validation.js`, `normalize.js`, `search-store.js`, `providers/demo.js`, затем адаптер одобренного API. Добавить `/flights` и разрешённые assets; существующий `/tickets` сохранить до отдельного решения о миграции.

Контракт адаптера: `capabilities`, `startSearch(query, context)`, `getResults(search, cursor)`, `revalidateOffer()` если поддерживается, `getBookingAction()` по клику. Один активный поставщик на поиск. Airports — отдельный сервис со справочником городов/аэропортов по миру, IATA, страной, timezone и локализованными названиями; источник/лицензию и HTTPS endpoint проверить перед импортом. Не отправлять запросы живых цен ради автодополнения.

Предлагаемые маршруты:

- `GET /api/flights/config`: режим и возможности без секретов.
- `GET /api/flights/locations?q=...&locale=...`: поиск аэропортов и городов, debounce, ограниченная выдача, кэш справочника.
- `POST /api/flights/searches`: валидация, запуск; возвращает внутренний searchId и статус.
- `GET /api/flights/searches/:id`: частичные результаты, cursor/version, pending/complete/failed, expiresAt. Опрос лишь уже начатого пользователем поиска, без нового background search.
- `POST /api/flights/searches/:id/offers/:offerId/booking`: проверка владельца, TTL и предложения; перепроверка при поддержке; возвращает действие, реально полученное от поставщика. Изменение цены требует показа новой цены перед переходом.

Нормализованный offer: внутренний id, provider, режим demo/live, время получения/истечения, itineraries outbound/return с segments, аэропорты, local times и timezone/UTC при наличии, durationMinutes, stops, marketing/operating carrier, seller proposals, total amount decimal string, currency, baggage по направлению/пассажиру, nullable logo/availability. Цена — за всех выбранных пассажиров и полный маршрут, без сборки фиктивного round trip из отдельных цен. Отсутствующие данные — null/«Не предоставлено».

Booking action должен поддерживать GET и при необходимости POST с параметрами, а не только строку URL. URL берётся с сервера поставщика, HTTPS, проверка допустимых доменов и отсутствие произвольного redirect от клиента. Provider results_url тоже проверяется по разрешённым upstream-доменам, чтобы исключить SSRF. Browser видит только наши id, не подписи/token/raw upstream.

## Защита и эксплуатация

- `FLIGHTS_ENABLED`, `FLIGHTS_PROVIDER=demo|...`, provider token/partner marker — серверные env; `.env.example` только с пустыми значениями. Отсутствие production ключей даёт явную недоступность live, а не молчаливую подмену тестовыми ценами.
- Валидация IATA, дат, класса, валюты, возраста/числа пассажиров с учётом capabilities. Правила infants у поставщиков могут различаться.
- Отдельный express-rate-limit, лимит одновременно выполняемых поисков, общий лимит/бюджет upstream. Search id связан с анонимной сессией или пользователем, случайный id не заменяет проверку владельца. SQLite аккаунтов и платежи не меняем.
- Bounded in-memory store с TTL и очисткой для одного процесса; Redis только при нескольких процессах и измеренной потребности. Кэш справочника отделён от живых результатов; не делимся поисками разных пользователей без разрешения API.
- Отдельные timeout запуска и общего асинхронного поиска; отмена клиентского ожидания, bounded retries для безопасного опроса, backoff на 429. Не повторять start/book автоматически без доказанной идемпотентности.
- 400 validation, 403 provider access, 429 с retry hint, 502/504 provider error, 410 expired. Пользовательские тексты через i18n; логи без ключей, подписей, booking URL и персональных данных.
- Перед live проверить настоящую цепочку Cloudflare→origin и trust proxy. Сейчас `trust proxy=1`; реальный IP необходим Travelpayouts. Не доверять произвольному заголовку CF-Connecting-IP на напрямую доступном origin.
- CSP расширяется точечно для подтверждённого HTTPS источника логотипов, иначе показывается имя/код компании. Поисковые результаты вынести на `/flights/search`, закрыть robots/noindex; `/flights` — индексируемая посадочная страница.

## Интерфейс и проверка

Поиск обеих точек по миру, обмен направлениями, one-way/round-trip, даты, взрослые/дети/младенцы, класс. Автодополнение с клавиатурной навигацией, Escape и aria; выбранный IATA сбрасывается при редактировании текста.

На телефоне поля в одну колонку, пассажиры и фильтры в удобных панелях, крупные кнопки. Карточка показывает оба направления и реальные предложения продавцов; сортировка по полной цене/суммарной длительности/пересадкам, фильтры авиакомпаний и локального времени вылета отдельно для направлений. Разные валюты напрямую не сравнивать.

Состояния: начальное, загрузка с частичными результатами, завершение, пустая выдача, фильтры скрыли всё, ошибка/лимит, истечение, изменение цены. Demo постоянно маркирован «Тестовые данные — не реальные цены», checkout отключён с объяснением, фиктивных ссылок нет. Demo использует fixtures только для явно поддержанных сценариев, не выдумывает рейсы на любой произвольный маршрут.

После согласования: тесты валидации и normalization, изоляции поисков, expired/reprice, upstream 429/timeout и безопасного booking action; UI one-way/return, все пассажиры, фильтры и сортировка, NO/EN/RU, клавиатура; desktop и ширины 360/390/768 без горизонтального overflow. Проверить OSL→JFK, SIN→SYD и межконтинентальные направления при live доступе. Выполнить существующий `test:static-security`, проверить прежние публичные страницы и что `.env`, data и lib недоступны HTTP. Нагрузку измерять ограниченной разрешённой серией, не фоновым сбором цен.

## Действия пользователя и порядок

1. Согласовать предложенный demo и архитектуру перед кодом, как указано в задаче.
2. Проверить текущие MAU по аналитике. Если 50 000+ подтверждены: зарегистрировать проект Travelpayouts, подготовить подтверждение трафика, прототип результатов, сценарий использования и объяснение необходимости API. При меньшем трафике — оценить официальные partner tools или отдельного metasearch-партнёра.
3. Для договора подтвердить Норвегию, рынок/валюты/локали, актуальную цену и квоты, airport codes, перенаправление и перепроверку offer, требования конверсии. Для Enterprise Amadeus запросить именно внешний booking deep link, не обычный Flight Offers Search.
4. Ключи вводить непосредственно в серверный `.env` после одобрения; не присылать в чат. Выдать доступ к staging/рабочему Git checkout перед production интеграцией.
5. Сначала demo без внешнего API, затем одобренный адаптер и contract tests по настоящим ответам, затем мобильная/регрессионная проверка, после этого отдельное согласование публикации.

В текущем анализе создан только этот документ. Код, зависимости, env и инфраструктура не изменены; production доступ и реальные переходы не проверены, поскольку аккаунтов/ключей нет.
